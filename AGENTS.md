# AGENTS.md

Guidance for coding agents working on this repository. `CLAUDE.md` and `GEMINI.md` are
symlinks to this file: edit `AGENTS.md` only.

## What this repository is

nanoglia runs TensorFlow Lite (`.tflite`) models **loaded at runtime** on microcontrollers,
through one `#![no_std]` API modelled on wasi-nn, with the best kernels of each chip. A Cargo
workspace:

| Crate | Role |
| --- | --- |
| `crates/nanoglia` | The library: `Graph` (load, select kernels, plan memory), `ExecutionContext` (arena, `compute`, `compute_with` and its `Observer`), `Registry`, `ModelReport` (every operator of a model with its kernel or the reason it has none, and the memory needed, without loading). |
| `crates/nanoglia-core` | Shared types (`TensorDesc`, `OpDesc`, `Error`/`ErrorCode`/`Detail`), the `Backend`/`Kernel` interface, TFLite-exact quantization math (`quant`), `Arena`, `Block`. |
| `crates/nanoglia-tflite` | Zero-copy, allocation-free, panic-free `.tflite` verifier and reader (own flatbuffer code, `#![forbid(unsafe_code)]`). |
| `crates/nanoglia-cmsis-nn-sys` | CMSIS-NN v8.0.0 as a git submodule (`cmsis-nn/`, do not edit; pin and bump procedure in the crate's README): integer kernels only, built with `cc`, hand-written FFI. |
| `crates/nanoglia-cmsis-nn` | CMSIS-NN backend: int8/int16 conv, int8 transpose conv, int8/int16 depthwise, FC, int8/int16 pooling, softmax, add, mul, pad, min/max. |
| `crates/nanoglia-esp-nn-sys` | ESP-NN v1.4.2 as a git submodule (`esp-nn/`, do not edit; pin and bump procedure in the crate's README): ANSI C kernels everywhere, ESP32-S3 optimized ones on `xtensa-esp32s3`; hand-written FFI and the ESP-NN scratch try-lock. |
| `crates/nanoglia-esp-nn` | ESP-NN backend (facade feature `esp-nn`, tried first): int8 conv, depthwise, FC, pooling, softmax, add, mul; runs the CMSIS-NN kernel when another context holds the ESP-NN lock. |
| `crates/nanoglia-kernels` | Pure-Rust backend: what CMSIS-NN lacks (reshape, transpose, slices, gather, split, arg max/min, resize, quantize, mean, LUT activations, broadcasting binary ops, int16 softmax/FC/logistic/tanh, the int8 transpose convs CMSIS-NN cannot run...) and float32. |
| `crates/nanoglia-c` | C API: opaque handle placed in the caller's buffer, `extern "C"` functions in `src/lib.rs`, the header `include/nanoglia.h` generated by cbindgen (`cbindgen.toml`), a CMake project (`CMakeLists.txt`) building `libnanoglia_c.a` with `cargo rustc --crate-type staticlib`, C tests and an example. An rlib for Cargo; features `std` (host) and `panic-handler` (bare metal) for the static library. |
| `crates/nanoglia-tools` | Host tool, the only crate with `std`: the binary `nanoglia`, whose `check <model.tflite>` prints what `ModelReport` finds (kernel or blocking reason of every operator, memory, `--json`, `--ram`, `--backends`). Bin-only, no dependency outside the workspace, its own registry of the three backends; published with the libraries (its own changelog and tag in `release-plz.toml`). |

Other directories: `fuzz/` (cargo-fuzz target `parse`, own workspace), `examples/nano33ble/`
(firmware for the Arduino Nano 33 BLE, own workspace), `examples/train-to-device/` (the code of the
train-and-deploy tutorial: training scripts as a uv project, a Rust program with its own workspace,
a C program, one committed reference model; `mise run example-train-to-device`, `train-to-device`), `emulation/` (test-runner firmware and its
Unicorn host for `mise run test-emulated`, own workspace and uv project), `hardware/` (what runs the golden cases on a real
board over its USB serial port, own workspace and uv project: `runner`, the protocol and the code that runs a case, shared
by `nano33ble`, the firmware of the Arduino Nano 33 BLE, and `emulated`, the same runner under Unicorn; `tools/`, the host
tool that flashes, runs, compares and writes the results), `tools/oracle/` (uv project generating
`testdata/` with LiteRT's reference kernels), `tools/check-no-malloc.sh`, `testdata/` (golden
cases, see `testdata/README.md`).

## Invariants

- `#![no_std]` everywhere except the host tool `nanoglia-tools`; no HAL, RTOS or SDK dependency
  (in the libraries: the board firmware of `hardware/nano33ble`, a test bench, uses embassy-nrf).
  The only C code is CMSIS-NN and ESP-NN (built without `ESP_PLATFORM`), pure C/assembly compiled
  with `cc`.
- **Every byte of dynamic memory comes from the allocator the caller passes**
  (`allocator_api2::alloc::Allocator`: `Global`, a custom one, or `Arena`). A graph makes one
  allocation, an execution context one, `compute` none. No C `malloc` (`mise run no-malloc`).
  `crates/nanoglia/tests/memory.rs` checks this; keep it passing.
- Model bytes are borrowed and never copied; constant buffers must be aligned for their type.
- Models are untrusted input: no panic on any model (`unwrap`, indexing, overflow); return
  `Error`. Fuzz with `mise run fuzz`.
- Kernels are **bit-exact with TFLite**: port the reference / TFLite Micro code (prepare and
  eval) faithfully, including whether scales are multiplied in `f32` or `f64`. Requantization
  uses double rounding by default (TFLite Micro, CMSIS-NN); the `single-rounding` feature
  switches every crate to `TFLITE_SINGLE_ROUNDING`.
- The C API checks every pointer, handle and size and returns a status; no panic may cross the
  boundary. After changing `crates/nanoglia-c/src/lib.rs`, run `mise run header` and commit
  the regenerated `include/nanoglia.h` (never edit it by hand; `mise run check-header` and CI
  fail otherwise), then `mise run test-c` and `mise run cross-c`. Keep C names in its doc
  comments (`nanoglia_load()`, `NANOGLIA_STATUS_OK`): they become the header's documentation.
- A backend's `select` returns a kernel only if it fully supports the operator, and the same
  kernel each time (loading selects twice); the kernel is a `&dyn Kernel` borrowed from the
  backend (the bundled backends lend `FnKernel` statics), and `Sync`: contexts may run it at the
  same time. `prepare` computes everything from the model, `eval` never reads the model and never
  allocates.
- **Every operator has a Cargo feature**, `op-<name>` in lower case with dashes (`op-conv-2d`),
  all on by default through `all-ops`: a firmware links only the kernels of the operators it
  names. To add an operator, or a kernel for one in another backend: put its arm in the backend's
  table behind `#[cfg(feature = "op-...")]` (and the module of its kernels behind the features of
  its operators), name the feature in `BuiltinOp::feature` (nanoglia-core), and declare it in the
  manifests of the backend, of `nanoglia` (forwarded to every backend that has the operator),
  `nanoglia-c` and `nanoglia-tools`, and in their `all-ops`. Features only add: never gate code
  on the absence of one. `crates/nanoglia-tools/tests/op_features.rs` fails until all of this
  agrees, and `mise run op-features` builds each feature alone. A build with
  `default-features = false` must name `all-ops` or its operators, or no model loads.

## Testing

With [mise](https://mise.jdx.dev): `mise install`, then `mise run check` (fmt, clippy, tests,
Arm cross builds) before pushing. CMSIS-NN and ESP-NN are git submodules: run `mise run
submodules` (`git submodule update --init --recursive`) after cloning and after a pinned commit
changes. Never edit their files; to bump one, follow the `-sys` crate's README (compare the
compiled files and the package list, run the golden suite), and keep the `include` list of its
`Cargo.toml` in sync with its build script (`mise run package`). Cargo goes through mbx (mr-boxington, a shared build cache);
do not run several builds in the same target directory at once.

- `crates/nanoglia/tests/golden.rs` runs every case of `testdata/` end to end.
  `testdata/pending.json` lists the cases expected to fail, with the reason; a listed case that
  passes fails the test. `emulation/tools/golden.py` reads the same list and repeats golden.rs's
  comparison and kernel checks, for `emulation/tools/run.py` and `hardware/tools`: change both
  together.
- `mise run oracle` regenerates `testdata/` (deterministic; LiteRT `BUILTIN_REF`). LiteRT's
  int8 and 16x8 FULLY_CONNECTED requantize in floating point, unlike TFLite Micro (issue #1).
- `mise run test-wasip1` runs the whole suite compiled to wasm32-wasip1 under wasmtime;
  `cross-arm`, `cross-riscv32`, `cross-wasm32` build the libraries without a global allocator.
- `mise run test-c` checks the C header, builds the C API with CMake (CMake and a host C
  compiler needed) and runs its C tests with CTest; `cross-c` builds it for thumbv7em and links
  it with `arm-none-eabi-gcc -nostdlib`.
- `mise run test-emulated` runs every golden case on a test-runner firmware under Unicorn:
  Cortex-M4F and M33 (CMSIS-NN's DSP code paths, checked to execute), M33 without DSP,
  Cortex-M0+ and riscv32imc; it also runs clippy on `emulation/` (`mise run fmt` checks its
  formatting). Host tests run CMSIS-NN's portable C code and ESP-NN's ANSI C code only. Emulated
  is not validated: Unicorn models no timing and takes alignment faults on its Cortex-M0 only
  (an unaligned `ldm` on a Cortex-M4 or M33 runs unnoticed), nothing has run on hardware yet (issue #2), and
  CMSIS-NN's Helium paths and ESP-NN's ESP32-S3 kernels have run nowhere. `mise run cross-esp32s3` builds the latter (toolchain:
  `mise run install-esp`). Say what you actually checked.
- `mise run test-hardware` tests `hardware/` without a board: the runner on the host behind a
  link in memory, then built for Cortex-M4F and driven by the host tool under Unicorn through
  every golden case, a panic, a fault, a hang and a firmware that crashes while starting; the
  host tool against a simulated device (`--dry-run`). `mise run build-hardware-nano33ble` builds
  the two images of the Nano 33 BLE (the MLPerf Tiny models are linked in and run from flash:
  only their cases are timed; the single-operator cases are received into RAM and check results
  only). `mise run test-hardware-nano33ble` flashes them with Arduino's `bossac` and runs the
  cases on a board plugged in over USB: **it has never run**, and neither has anything in
  `hardware/nano33ble/src/main.rs` (USB, clock, cycle counter, watchdog, resets); the how-to
  "run the golden cases on a board" lists it. Keep the hardware-only code there, thin, and
  everything else in `runner` or the host tool, where it is tested. The firmware has no code
  that erases or writes a page of flash; `embassy_nrf::init` holds a UICR routine that the
  configuration of the firmware keeps from writing (`reset-pin-as-gpio`, debug port and regulator
  left alone): keep it so. Every crash handler counts the crash itself (`boot::crash`) and resets
  into the bootloader at the third in a row; the waits of the host tool are derived from the
  constants of the firmware (`WATCHDOG_S`, `MAX_FAILED_BOOTS`, `NO_CONTACT_S` in
  `protocol.py`): change them together. The protocol is described in `hardware/runner/src/lib.rs` and `frame.rs`, and
  mirrored in `hardware/tools/nanoglia_hardware/protocol.py` and `simulated.py`: change them
  together. Do not write a time or a result as measured on a board unless it was.

## CI and releases

`.github/workflows/ci.yml` mirrors the mise tasks (fmt, clippy, tests, C API, cross builds, wasm,
no-malloc, firmware, the board runner without its board, cargo-deny, MSRV, docs, fuzz). `coverage.yml` uploads `mise run coverage`
to Codecov. `release.yml` runs release-plz (`release-plz.toml`): a release PR with versions and
changelogs from the commit messages, then publication. `pr-title.yml` checks PR titles.

## Documentation

User documentation lives in `documentation/` and follows [Diátaxis](https://diataxis.fr);
`documentation/README.md` is the index. `tutorials/` are lessons followed from start to finish,
`how-to-guides/` reach one goal each, `explanation/` says why, `reference/` lists every item and
number.

- Full words in file and directory names (`how-to-guides`, `development-tasks`), relative links
  between pages. Add new pages to the index and to the Documentation table of the root
  `README.md`.
- Check every API name, signature, feature, size and default against the source, and every
  number against a command you ran (say which, with the machine, date and commit). Quote time
  and memory figures only from `reference/performance.md` and `reference/memory.md`, with a link.
- Describe users generically ("your application", "an embedded OS"). Do not present host or
  wasmtime timings as microcontroller numbers, and keep the hardware-validation status (issue #2)
  visible where it matters.
- When a change lands, update: `reference/supported-operators.md` (a `select`/`plan` condition,
  a kernel or an operator), `reference/features.md` (Cargo features, those of `nanoglia-tools` too;
  the table of operator features for a new operator), `reference/errors.md` (an
  `Error`, `ErrorCode` or `Detail` returned by a public function), `reference/memory.md` (the
  allocation contract or the block layout; re-measure the MLPerf Tiny footprints with
  `cargo test -p nanoglia --test memory -- --nocapture`; its code-size table after a change of
  what a firmware links, with `mise run example-nano33ble` per feature set), `reference/performance.md` (after
  `mise run bench` / `bench-wasm` on a performance change), `reference/development-tasks.md`
  (`mise.toml` or `.github/workflows/`), and the tutorial or guides whose code or output changes
  (run their code again; the output of `nanoglia check` is quoted in
  `how-to-guides/check-whether-a-model-runs.md` and `crates/nanoglia-tools/README.md`). `tutorials/train-and-deploy.md` quotes `examples/train-to-device`: keep
  its code blocks and outputs equal to the example's sources and to a run of `mise run
  train-to-device`.

## Conventions

- Rust 2024, MSRV 1.89, `cargo fmt`; English code and documentation; document public items.
- Commit messages and PR titles follow Conventional Commits (`feat:`, `fix:`, `perf:`,
  `refactor:`, `docs:`, `test:`, `build:`, `ci:`, `chore:`), with a body explaining the why.
- No AI attribution: no `Co-Authored-By` trailers for assistants, no "generated with" lines.
- Design notes and plans stay out of the repository.
- A workaround kept in the repository (build, CI, release, oracle, C libraries) gets a comment next
  to it and an entry in the matching issue labelled `workaround` (#26 build/CI/release, #27 oracle
  and bit-exactness, #28 CMSIS-NN/ESP-NN): what, why, where, and when it can be removed.
- A bug or limitation found in a dependency (CMSIS-NN, ESP-NN, LiteRT, ...) gets a GitHub issue
  with the `upstream` label: upstream version and link to the exact lines, the problem, the
  impact on nanoglia and the workaround (with its file), and the steps to report or drop it.
