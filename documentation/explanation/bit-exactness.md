# Bit-exactness

For quantized models, nanoglia computes the same integers as TensorFlow
Lite, bit for bit. This page explains why that matters, how it is
achieved and checked, where the reference itself is ambiguous, and why
nanoglia reads TFLite models rather than ONNX ones.

## Why bit for bit

A quantized model is integer arithmetic: given the same inputs, a
correct implementation can produce exactly one output. Matching TFLite
exactly brings three things:

- **The accuracy you measured is the accuracy you ship.** You evaluate a
  converted model with LiteRT on your computer; if the device computes
  the same integers, its accuracy is the same, with no new error to
  track.
- **Testing is simple.** An output is right or wrong; there is no
  tolerance to choose, and a difference of one unit is a bug to explain.
- **Backends are interchangeable.** CMSIS-NN and the Rust kernels give
  the same result for the operators both can run, so the registry can
  pick the fastest one without changing the model's behaviour.

Float32 kernels follow the same loops and accumulation order as the
reference kernels, and are checked to a relative tolerance of 1e-5
(`testdata/README.md`): float results depend on the compiler and the
FPU, and the same bits are not guaranteed.

## How

Each kernel ports the TensorFlow Lite code, both the preparation and
the evaluation:

- the CMSIS-NN backend ports the preparation of TensorFlow Lite Micro's
  CMSIS-NN kernels (`kernels/cmsis_nn/*.cc`), then calls the same
  CMSIS-NN functions;
- the ESP-NN backend ports the preparation of esp-tflite-micro's ESP-NN
  kernels and TensorFlow Lite Micro, then calls the same ESP-NN
  functions, and claims only the operators whose CMSIS-NN kernel gives
  the same result (it falls back to it when ESP-NN is busy);
- the Rust backend ports the reference kernels of TFLite (the
  `BUILTIN_REF` resolver), with their preparation code.

"Faithfully" includes details that change the last bit: whether a scale
product is computed in `f32` or `f64` (convolutions compute
`double(input) * double(filter) / double(output)`), how a real
multiplier becomes a 32-bit multiplier and a shift
(`quant::quantize_multiplier`), how lookup tables are filled, and how
values round (`round` half away from zero, `RoundingDivideByPOT`).
These functions live in `nanoglia_core::quant`.

## The oracle

`testdata/` holds the expected outputs, generated by `mise run oracle`
(`tools/oracle/generate.py`) with the LiteRT Python interpreter
(`ai-edge-litert` 2.3.0, locked in `tools/oracle/uv.lock`) and its
reference kernels:
`Interpreter(..., experimental_op_resolver_type=OpResolverType.BUILTIN_REF)`.
The reference kernels are the plain C++ implementations TFLite
specifies its operators with, and they compute the same results as
TensorFlow Lite Micro.

There are 413 cases:

- 398 single-operator models written by the generator, mostly in
  int8, 16x8 and float32 versions (plus integer and boolean ones), with weights and output ranges calibrated as a
  converter would;
- 3 random inputs for each of the 5 MLPerf Tiny models.

`crates/nanoglia/tests/golden.rs` runs every case end to end and
requires quantized outputs to match exactly. 410 cases pass; the 3
`ad01_int8` samples are listed in `testdata/pending.json` (see below).
The test fails if a pending case starts to pass, so the list stays
current. The same tests run compiled to WebAssembly under wasmtime
(`mise run test-wasip1`).

`mise run test-emulated` runs the same cases, compared the same way, on
a firmware built for Cortex-M4F, Cortex-M33 (with the DSP extension),
Cortex-M0+ and riscv32imc, under the Unicorn instruction-set emulator.
On the M4 and M33 builds, CMSIS-NN compiles its DSP code paths, and the
run checks that their packed-SIMD instructions (`smlad`, `sxtb16`,
`pkhbt`...) execute. A fifth build, Cortex-M33 with the DSP extension
turned off, and the M0+ build must hold no DSP instruction at all. All
five builds passed the 373 cases and failed the 3 pending ones on their
output values, as the host does (`mise run test-emulated`, Unicorn
2.1.4, on a Linux 6.12 aarch64 virtual machine, 2026-11-10, this
change on top of commit `3d382f8`).

The emulator runs the instructions, not the chip: it has no timing,
caches or flash wait states. Unicorn's Cortex-M0 faults on an unaligned
access, as Armv6-M does, but an unaligned `ldm` on the Cortex-M4 or M33,
or a misaligned load on a RISC-V core without support for it, faults on
hardware and runs unnoticed here.

The golden cases run a second time with the ESP-NN backend first
(`cargo test -p nanoglia --features esp-nn --test golden`, part of
`mise run test`), and the test checks that ESP-NN ran some operators.

What the oracle does not cover: on the host, CMSIS-NN compiles its
portable C code and ESP-NN its ANSI C kernels. CMSIS-NN's DSP code paths
match the golden data under the emulator, and on one real Cortex-M4F: on
an Arduino Nano 33 BLE, on 2026-11-10, 373 of the 376 golden cases gave
LiteRT's bytes (the float32 ones: within their tolerance of 1e-5), the
other 3 the `ad01_int8` difference (issue #1, below), as on the host
([run the golden cases on a board](../how-to-guides/run-the-golden-cases-on-a-board.md#what-has-run-on-a-board)).
That is one board and one session. CMSIS-NN's Helium paths and ESP-NN's
ESP32-S3 kernels are written to give the same results but have not run
against the golden data at all, and no other chip has run the golden
cases (issue #2).

## Single and double rounding

Quantized kernels rescale their 32-bit accumulators with a fixed-point
multiplier: `x × multiplier × 2^shift`. TFLite has two ways to round
this product:

- **Double rounding** (the default of TensorFlow Lite Micro and
  CMSIS-NN): gemmlowp's `SaturatingRoundingDoublingHighMul` rounds the
  product to 32 bits, then `RoundingDivideByPOT` rounds the shift.
- **Single rounding** (`TFLITE_SINGLE_ROUNDING`): the 64-bit product is
  shifted and rounded once. It is cheaper, and the results differ from
  double rounding by one unit in rare cases.

nanoglia uses double rounding, like the golden data. The
`single-rounding` feature switches every crate, CMSIS-NN included
(`CMSIS_NN_USE_SINGLE_ROUNDING`), to single rounding, for firmware built
against a TFLite configured that way. ESP-NN has no single-rounding
mode, so the ESP-NN backend then claims nothing. Results differ from the
golden data by design: CI builds this mode (clippy with all features)
but does not run the golden tests with it.

## Where LiteRT and TensorFlow Lite Micro disagree

The reference is not always one implementation. When LiteRT's reference
kernels and TensorFlow Lite Micro compute differently, nanoglia follows
TensorFlow Lite Micro and CMSIS-NN, which run on microcontrollers, except
where noted:

- **`FULLY_CONNECTED` requantization (issue #1).** LiteRT's reference
  fully-connected kernel, in int8 and 16x8, requantizes its accumulator
  in floating point (`round(acc * scale)`), while TensorFlow Lite Micro
  and CMSIS-NN use the fixed-point multiplier. The two agree almost
  always. The anomaly-detection model `ad01_int8` stacks ten
  fully-connected layers, and its outputs drift by one or two units from
  LiteRT's: its three golden samples are pending until the oracle can
  produce the TensorFlow Lite Micro result. The other MLPerf Tiny models
  have one fully-connected layer and match. The single-layer case
  `fully_connected_per_channel_int16` happens to match LiteRT on its 16
  outputs; other data may differ by one.
- **`MUL` multiplier.** nanoglia computes `input1_scale * input2_scale /
  output_scale` in `f64`, like TensorFlow Lite Micro and CMSIS-NN;
  LiteRT rounds the product of the scales to `f32` first. The golden
  `MUL` cases match.
- **int16 `SOFTMAX`.** Here nanoglia follows LiteRT: its lookup tables are
  computed in `f64`, while TensorFlow Lite Micro computes them in `f32`,
  which changes two entries of one table.
- **int16 `LOGISTIC` output scale.** Both compute the int16 `LOGISTIC` and
  `TANH` the same way, but LiteRT's reference `LOGISTIC` requires an output
  scale of exactly 1/32768, while TensorFlow Lite Micro accepts any scale
  within 0.07 % of it (its `CheckedLog2` test). nanoglia claims only what
  both accept.
- **int8 `TRANSPOSE_CONV` activation.** TensorFlow Lite Micro's CMSIS-NN
  kernel passes `kTfLiteActNone` when it computes the activation range,
  so it ignores the fused activation of the options (operator version
  4). nanoglia follows LiteRT and applies it, on both backends.
- **Floating-point contraction.** LiteRT's wheels are compiled by Clang,
  which fuses `a * b + c` within an expression into one multiply-add on
  AArch64, where the golden data is generated. nanoglia reproduces these
  fusions (`mul_add`) in the float convolutions and in `RESIZE_BILINEAR`,
  whose uint8 results otherwise differ by one on some values. A TensorFlow
  Lite Micro build by another compiler may fuse differently.
- **Vectorized sums.** Where Clang vectorizes a reference loop instead,
  the rounding changes again: in the sums of `BATCH_MATMUL` and
  `L2_NORMALIZATION`, LiteRT's AArch64 build rounds each product of the
  first multiple of eight terms and adds them in order, then fuses the
  multiply-add of the terms left. Measured against LiteRT for every length
  from 1 to 40, nanoglia does the same (`dot_by_eight`), and these golden
  cases match bit for bit.
- **Eigen's functions.** LiteRT's float `GELU` evaluates `tanh` and `erfc`
  with Eigen's approximations, in packets of four values and a scalar tail,
  and Eigen's packet `erfc` uses the NEON reciprocal estimate where the
  scalar one divides. nanoglia ports these functions as LiteRT's AArch64
  build computes them, packet and tail included, and matches it on every
  one of the 2^32 inputs of the packet code, for both variants, and on 12
  million samples of the tail (a comparison run on a Linux aarch64
  virtual machine, 2026-11-14, with the LiteRT 2.3.0 wheel of
  `tools/oracle/uv.lock`, this change on top of commit `c7a6547`).

A backend refuses an operator rather than compute it differently from
TFLite. For example, CMSIS-NN's int16 softmax is not used (it does not
clamp its result), int16 `ADD` and `SUB` with power-of-two scales are
refused (TFLite runs another kernel, chosen by an option nanoglia does
not decode), 16x8 layers with an int32 bias are refused (LiteRT would
read the bias as int64), and the 16x8 `CONV_2D`, `DEPTHWISE_CONV_2D` and
`FULLY_CONNECTED` of CMSIS-NN are claimed only when their accumulators
cannot overflow the 32-bit intermediate value of CMSIS-NN's requantization
(TFLite keeps 64 bits). See [Supported operators](../reference/supported-operators.md).

## Why TFLite and not ONNX

ONNX is the most common exchange format for trained models, and most
PyTorch models can be exported to it. nanoglia reads TensorFlow Lite
(LiteRT) models instead, for four reasons:

- **Read in place.** A `.tflite` file is a flatbuffer: tables of offsets
  that can be verified once and then read where they are, in flash,
  without copying or decoding. An ONNX file is a protocol buffer, whose
  variable-length encoding must be parsed into memory before use;
  reading the weights in place from flash, without a heap, is not what
  the format is built for.
- **Defined integer semantics.** A TFLite int8 operator is an integer
  operator: the quantization parameters of every tensor, the bias type,
  the multipliers and the rounding are fixed by the reference kernels,
  so there is one correct output to match. Quantized ONNX models are
  mostly expressed in the QDQ form, `QuantizeLinear` / `DequantizeLinear`
  pairs around float operators; how the integer computation in between is
  carried out (accumulator, rescaling, rounding) is left to each runtime.
- **NHWC.** TFLite tensors are channels-last, the layout CMSIS-NN and
  ESP-NN kernels expect. ONNX models are usually channels-first and would
  need transposes or a layout pass.
- **The microcontroller ecosystem.** TensorFlow Lite Micro, CMSIS-NN and
  ESP-NN are written against TFLite's operator semantics, and the
  LiteRT converters produce models for them. nanoglia can port their
  code and test against their reference.

An existing ONNX model can still be used: convert it to a full-integer
`.tflite` file first ([Convert a PyTorch model](../how-to-guides/convert-a-pytorch-model.md#from-an-onnx-model)).
