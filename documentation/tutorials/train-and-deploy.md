# From training to the device

In this tutorial you take a neural network all the way from a training
script to the code that runs it on a device. You train a small gesture
classifier on accelerometer data, with Keras or with PyTorch, quantize it
and export it to a `.tflite` file, check that nanoglia can run it, then
run it from Rust and from C and compare every output with the one the
Python side computed.

Everything runs on your computer, so you need no board, and the data is
generated by the script, so you download no dataset. By the end you will
have seen each hand-over of the path: from float weights to an int8
model, from the model file to a program, and from the accelerometer's
values to the model's input and back to a probability.

[Your first inference](first-inference.md) explains the Rust API step by
step; follow it first if you have never used nanoglia.

## What you need

- Git, and [uv](https://docs.astral.sh/uv/), which installs Python and
  the training packages.
- Rust 1.89 or later and a C compiler (`gcc` or `clang`); for the C
  program of step 7, CMake 3.21 or later.
- For the PyTorch track, x86_64 Linux or macOS on Apple silicon: the
  converter (`litert-converter`) ships no other wheels. TensorFlow, for
  the Keras track, also has wheels for aarch64 Linux and Windows; the
  training scripts were run on x86_64 Linux only.

The training packages are large (the TensorFlow wheel for x86_64 Linux
is 573 MB): uv installs only those of the track you run.

## 1. Get the code

The training scripts are in nanoglia's repository, in
`examples/train-to-device`. Clone it with its submodules (CMSIS-NN, the C
kernels nanoglia compiles):

```sh
git clone --recurse-submodules https://github.com/AlixANNERAUD/nanoglia
cd nanoglia
```

## 2. Look at the task

The model classifies two seconds of accelerometer data, 50 samples of
the three axes at 25 Hz, in g, as one of three gestures:

- `idle`: the board lies roughly flat and still;
- `shake`: a fast oscillation (3 to 6 Hz) along one direction;
- `circle`: a slower rotation (0.8 to 2 Hz) in the horizontal plane.

`training/gesture.py` generates the windows from these descriptions,
with gravity, a slow drift and sensor noise, from a fixed seed: 1500
windows to train on and 600 to test on. Weak gestures come close to the
noise, so a few windows are hard to tell apart and the accuracy stays
below 100 %.

The network is the same in both frameworks, 835 parameters in all:

| Layer | Output shape | Parameters |
| --- | --- | --- |
| input: 50 samples × 3 axes, one channel | 50 × 3 × 1 | |
| convolution, 8 filters of 5 × 3, ReLU | 46 × 1 × 8 | 128 |
| max pooling, 2 × 1 | 23 × 1 × 8 | |
| convolution, 16 filters of 5 × 1, ReLU | 19 × 1 × 16 | 656 |
| global average | 16 | |
| dense, then softmax | 3 | 51 |

The first convolution spans the three axes, so everything after it works
along time only.

## 3. Train, quantize and export

Take one of the two tracks. Both write the same things, and the rest of
the tutorial is the same for both; it shows the Keras outputs, and step 8
shows the PyTorch ones. If you take the PyTorch track, write `pytorch`
wherever a later command says `keras`: your outputs are those of step 8
(7 operators instead of 6, and slightly larger sizes).

A microcontroller computes in integers, so the model must be converted
to **full-integer quantization**: int8 weights, int8 activations, and an
int8 input and output. The converter needs to see typical inputs to
choose the scale of each activation; both scripts give it 200 training
windows (the calibration, or representative, data).

### With Keras

```sh
uv run --locked --project examples/train-to-device/training --group keras \
    python examples/train-to-device/training/train_keras.py target/train-to-device/keras
```

`train_keras.py` builds and trains the network, then converts it with
TensorFlow's converter:

```python
def representative_dataset():
    for window in train_x[: gesture.CALIBRATION_WINDOWS]:
        yield [window[None]]

converter = tf.lite.TFLiteConverter.from_keras_model(model)
converter.optimizations = [tf.lite.Optimize.DEFAULT]
converter.representative_dataset = representative_dataset
# Integer kernels only, and an int8 interface: no float operator may remain.
converter.target_spec.supported_ops = [tf.lite.OpsSet.TFLITE_BUILTINS_INT8]
converter.inference_input_type = tf.int8
converter.inference_output_type = tf.int8
```

The last three lines matter: without them the converter may keep float
operators, and keeps a float input and output
([LiteRT's guide](https://developers.google.com/edge/litert/conversion/tensorflow/quantization/post_training_integer_quant)).

### With PyTorch

```sh
uv run --locked --project examples/train-to-device/training --group pytorch \
    python examples/train-to-device/training/train_pytorch.py target/train-to-device/pytorch
```

`train_pytorch.py` trains the network, then quantizes it with PyTorch's
PT2E flow and litert-torch's quantizer, as
[Convert a PyTorch model](../how-to-guides/convert-a-pytorch-model.md)
describes, and converts it:

```python
quantizer = PT2EQuantizer().set_global(get_symmetric_quantization_config(is_per_channel=True))
sample_args = (train_x[:1],)
prepared = prepare_pt2e(torch.export.export(model, sample_args).module(), quantizer)
with torch.no_grad():
    for i in range(gesture.CALIBRATION_WINDOWS):
        prepared(train_x[i : i + 1])
quantized = convert_pt2e(prepared, fold_quantize=False)
edge_model = litert_torch.convert(
    quantized, sample_args, quant_config=QuantConfig(pt2e_quantizer=quantizer)
)
```

Two things differ from Keras, both handled in the script:

- litert-torch keeps the float input and output of the PyTorch model:
  the converted file starts with a `QUANTIZE` operator and ends with a
  `DEQUANTIZE`. `strip_float_interface` removes them and makes their
  int8 tensors the model's input and output, which is what
  `inference_input_type = tf.int8` does in TensorFlow's converter.
- litert-torch 0.10.0's quantizer leaves `torch.softmax` in float32. The
  model calls `torch.ops.aten._softmax` instead, the form of softmax the
  quantizer knows.

### Read the report

Whichever track you took, the report says what the device will run:

- every operator reads and writes `int8` (biases and shapes are `int32`
  constants). The script stops with an error if a float operator
  remains;
- the input is int8 with a scale and a zero point: the device must turn
  the accelerometer's values into these integers (step 6);
- the float model and the int8 model agree on the test set: the
  quantization cost no accuracy here. The int8 accuracy comes from
  LiteRT, Google's runtime for `.tflite` models, running the exported
  file with its reference kernels;
- the last lines show the int8 scores of six test windows, the class
  with the highest score and its probability.

The outputs above come from a GitHub `ubuntu-latest` runner (Ubuntu

Every operator has a kernel, and the model needs about 2.2 KiB of RAM
on top of its 5 KiB of flash: it fits the 256 KiB given as budget, which
is the RAM of an Arduino Nano 33 BLE. Had an operator been unsupported,
the command would list each one and exit with status 1
([Check whether a model runs](../how-to-guides/check-whether-a-model-runs.md)).

The same check can be made from code, which is also the first half of
the program a firmware runs. Loading the model is that check: `Graph::load_in` verifies the file,
chooses a kernel for each operator and plans the memory, or returns an
error that names the operator it cannot run. Create a project next to
the clone, add nanoglia from the clone, and copy the model into it:

```sh
cd ..
cargo new gesture
cd gesture
cargo add nanoglia --path ../nanoglia/crates/nanoglia --no-default-features \
    --features cmsis-nn,kernels,op-conv-2d,op-depthwise-conv-2d,op-fully-connected,op-max-pool-2d,op-mean,op-reshape,op-softmax
cp ../nanoglia/target/train-to-device/keras/model.tflite .
```

These features are all the model needs. `cmsis-nn` brings the C kernels
and `kernels` the operators CMSIS-NN lacks. Each `op-` feature brings
the kernels of one operator of the list the training script printed:
`op-conv-2d` for `CONV_2D`, and so on (the PyTorch model needs neither
`op-depthwise-conv-2d` nor `op-reshape`). nanoglia loads models at run
time, so it cannot know which operators a firmware needs: by default it
builds them all, with the float32 and int16 kernels. Naming the
operators, and leaving out the default `float` and `int16` features,
keeps the rest out of the firmware
([Reduce the code size](../how-to-guides/reduce-code-size.md)).

Replace the content of `src/main.rs` with:

```rust
use nanoglia::{Arena, Encoding, Graph, Target};

/// The model bytes, placed on a 16-byte boundary so that its constant buffers are aligned.
#[repr(C, align(16))]
struct Aligned<T: ?Sized>(T);

static MODEL: &Aligned<[u8]> = &Aligned(*include_bytes!("../model.tflite"));

/// All the memory nanoglia may use: the graph and one execution context.
static mut MEMORY: [u8; 8 * 1024] = [0; 8 * 1024];

fn main() -> Result<(), Box<dyn std::error::Error>> {
    // SAFETY: `main` runs once and is the only user of `MEMORY`.
    let arena = Arena::new(unsafe { &mut *core::ptr::addr_of_mut!(MEMORY) });

    // Load the model: verify it, choose a kernel for each operator, plan the memory.
    let graph = Graph::load_in(&[&MODEL.0], Encoding::Autodetect, Target::Auto, &arena)?;
    println!(
        "model {} B, {} operators, graph {} B, context {} B",
        MODEL.0.len(),
        graph.operator_count(),
        graph.graph_bytes(),
        graph.context_bytes()
    );
    for i in 0..graph.operator_count() {
        println!("  operator {i}: {}", graph.kernel_name(i).unwrap_or("?"));
    }
    let input = graph.input(0)?;
    let (scale, zero_point) = (input.quant.scale(), input.quant.zero_point());
    println!(
        "input: {:?} {:?}, scale {scale}, zero point {zero_point}",
        input.dtype, input.dims
    );

    Ok(())
}
```

This is how a firmware holds a model: `include_bytes!` puts the file in
the program (in flash, on a microcontroller), aligned so that nanoglia
reads the weights in place, and every byte nanoglia uses comes from the
static buffer `MEMORY`, through an `Arena`. There is no heap.

```sh
cargo run --release
```

The model loads: each of the six operators the training script listed

## 6. Run it in Rust

Now feed the model the six test windows. Add the class names after
`MEMORY`:

```rust
/// The classes of the model, in the order of its outputs.
const LABELS: [&str; 3] = ["idle", "shake", "circle"];
```

and replace the final `Ok(())` of `main` with:

```rust
    // The directory of the test vectors, from the command line.
    let vectors = std::env::args()
        .nth(1)
        .ok_or("usage: gesture VECTORS_DIRECTORY")?;

    // The execution context holds the activations of one inference.
    let mut ctx = graph.init_execution_context_in(&arena)?;
    println!("arena: {} of {} bytes used", arena.used(), arena.capacity());

    let mut samples = 0;
    let mut matches = 0;
    while let Ok(window) = std::fs::read(format!("{vectors}/sample_{samples}/window.bin")) {
        // The accelerometer window: 50 samples of 3 axes, float32, in g.
        let window = window
            .as_chunks::<4>()
            .0
            .iter()
            .map(|b| f32::from_le_bytes(*b));

        // Quantize it into the input tensor: q = round(x / scale) + zero_point.
        let mut tensor = ctx.input_mut(0)?;
        let quantized = tensor.as_mut_slice::<i8>()?;
        for (q, x) in quantized.iter_mut().zip(window) {
            *q = ((x / scale).round() as i32 + zero_point).clamp(-128, 127) as i8;
        }
        let expected = std::fs::read(format!("{vectors}/sample_{samples}/input_0.bin"))?;
        let same_input = quantized.iter().map(|&q| q as u8).eq(expected);

        ctx.compute()?;

        // Dequantize the best score: probability = scale * (q - zero_point).
        let output = ctx.output(0)?;
        let quantization = output.quantization();
        let scores = output.as_slice::<i8>()?;
        // The first of the highest scores, as NumPy's `argmax`.
        let best = (1..scores.len()).fold(0, |b, i| if scores[i] > scores[b] { i } else { b });
        let probability =
            quantization.scale() * (i32::from(scores[best]) - quantization.zero_point()) as f32;

        let expected = std::fs::read(format!("{vectors}/sample_{samples}/output_0.bin"))?;
        let same = same_input && scores.iter().map(|&q| q as u8).eq(expected);
        println!(
            "sample_{samples}: {scores:4?} -> {:6} {probability:.3}  {}",
            LABELS.get(best).copied().unwrap_or("?"),
            if same {
                "same as LiteRT"
            } else {
                "DIFFERS from LiteRT"
            }
        );
        samples += 1;
        matches += usize::from(same);
    }

    println!("{matches} of {samples} samples match LiteRT");
    if samples == 0 || matches != samples {
        return Err("the outputs are not LiteRT's".into());
    }
    Ok(())
```

Three parts of the loop are what a firmware does for each window; the
rest reads the test vectors and compares.

- **Quantize.** The model's input is int8: a value `x` in g is stored as
  `round(x / scale) + zero_point`, saturated to the int8 range. The loop
  writes the result straight into the input tensor, inside the arena.
  On a device, `window` comes from the accelerometer driver instead of a
  file.
- **Compute.** `compute` runs the six operators and allocates nothing.
- **Dequantize.** The scores are int8 too: `scale * (q - zero_point)`
  turns the best one into a probability between 0 and 1.

Open `gesture.c`: it does what the Rust program does, in the same order.

**The model is compiled into the program.** C has no `include_bytes!`
before C23, so the build turns the file into a list of bytes that an
array initializer includes:

```c
/* The model bytes, on a 16-byte boundary (NANOGLIA_MODEL_ALIGNMENT): const, so in flash. */
static _Alignas(NANOGLIA_MODEL_ALIGNMENT) const uint8_t model[] = {
#include "model.inc"
};
```

`model.inc` holds `0x20,0x00,0x00,0x00,0x54,0x46,...`. The CMake project
writes it with `c/embed.cmake`; by hand, `xxd` writes the same list when
it reads its standard input:

```sh
xxd -i < target/train-to-device/keras/model.tflite > model.inc
```

Declaring the array yourself is what lets you align it: nanoglia reads
the weights in place and refuses a model that does not start on a
16-byte boundary. (`xxd -i model.tflite`, with the file as an argument,
writes a whole declaration instead, without the alignment.)
[Use nanoglia from C](../how-to-guides/use-from-c.md#put-the-model-in-the-program)
shows two other ways, the assembler's `.incbin` and C23's `#embed`.

**One buffer holds all the memory**, and `nanoglia_load` places the
handle, the graph and the execution context in it:

```c
static unsigned char memory[8 * 1024];
...
nanoglia *nn;
if (nanoglia_load(model, sizeof model, memory, sizeof memory, &nn, &error) != NANOGLIA_STATUS_OK) {
    return fail("load", &error);
}
```

**Quantize, compute, dequantize** are the three steps of the Rust loop.
`nanoglia_input` gave `input`, whose `data` points at the input tensor
and whose `scale` and `zero_point` are the model's:

```c
int8_t *quantized = input.data;
for (size_t i = 0; i < WINDOW; i++) {
    long q = lroundf(window[i] / input.scale) + input.zero_point;
    quantized[i] = (int8_t)(q < -128 ? -128 : q > 127 ? 127 : q);
}
...
if (nanoglia_compute(nn, &error) != NANOGLIA_STATUS_OK) {
...
float probability = output.scale * (float)(scores[best] - output.zero_point);
```

`lroundf` rounds halves away from zero, as `f32::round` does in Rust and
as the Python script does on purpose (NumPy's `round` would round them
to the nearest even integer): the three sides quantize a window to the
same bytes.

## 8. Compare

You now have three computations of the same six windows: LiteRT in
Python, nanoglia from Rust, nanoglia from C. With the Keras model:

| Window | True class | LiteRT (Python) | nanoglia (Rust) | nanoglia (C) | Answer |
| --- | --- | --- | --- | --- | --- |
| `sample_0` | idle | 126, -128, -127 | 126, -128, -127 | 126, -128, -127 | idle 0.992 |
| `sample_1` | shake | -128, 127, -128 | -128, 127, -128 | -128, 127, -128 | shake 0.996 |
| `sample_2` | circle | -128, -128, 127 | -128, -128, 127 | -128, -128, 127 | circle 0.996 |
| `sample_3` | idle | 127, -128, -128 | 127, -128, -128 | 127, -128, -128 | idle 0.996 |
| `sample_4` | shake | -128, 127, -128 | -128, 127, -128 | -128, 127, -128 | shake 0.996 |
| `sample_5` | circle | -125, -128, 125 | -125, -128, 125 | -125, -128, 125 | circle 0.988 |

The three columns are equal, which is the point of the comparison:
nanoglia's kernels reproduce LiteRT's reference kernels bit for bit
([Bit-exactness](../explanation/bit-exactness.md)), so the accuracy you
measured in Python at step 3 is the accuracy of the device. You do not
need to measure it again on the target, only to check a few vectors.

With the PyTorch model, the same commands with `pytorch` in place of
`keras` give, from the Rust program:

The program did not change: it reads the scale, the zero point and the

is the first of the two, `idle`: a wrong answer, from a model that is
right on 97.67 % of the test windows. nanoglia gives the same wrong

trained is good enough is the accuracy of step 3.

## 9. Next: on a microcontroller

Your Rust program already uses nanoglia the way a firmware does: the
model in a static, the memory in a static buffer, no heap. Three things
change on a board:

- the program is `#![no_std]`, and the window comes from the
  accelerometer driver, 50 samples at 25 Hz, instead of `window.bin`;
- CMSIS-NN is compiled for the target, where it uses the DSP or Helium
  instructions of the core: its scratch memory can then differ, so
  compute the size of `MEMORY` for the target
  ([Size the memory](../how-to-guides/size-memory.md));
- the comparison of step 8 is worth keeping: embed one test window and
  its expected scores, and check them at start-up.

[Run on a microcontroller](../how-to-guides/run-on-a-microcontroller.md)
gives the steps for a Cortex-M or ESP32-S3 firmware, and
[`examples/nano33ble`](../../examples/nano33ble) is a complete firmware
for the Arduino Nano 33 BLE, a board that carries an accelerometer. For
C firmware, see
[Use nanoglia from C](../how-to-guides/use-from-c.md#link-it-into-a-firmware).

> The outputs of this tutorial were computed on computers. nanoglia has
> not been validated on hardware yet: its kernels run under an emulator
> in CI, without timing, and this is tracked in issue #2.
